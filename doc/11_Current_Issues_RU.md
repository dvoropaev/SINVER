# 11. Текущие проблемы

[← Назад](10_DNS_RU.md) · [Содержание](README_RU.md#содержание) · [Вперёд → на главную](README_RU.md)

Глава описывает подтверждённые ограничения и ошибки версии **0.0.0** в ветке `doc`. Они важны при настройке доступа, изменении инвентаря и публикации DNS. Для рабочей инфраструктуры сначала проверьте выбранный сценарий на отдельной зоне и подготовьте восстановление данных.

## Доступ и эксплуатация

| Проблема | Последствие | Как действовать |
| --- | --- | --- |
| Нет встроенных пользователей, входа и разграничения прав | Любой получивший доступ к SINVER может редактировать инвентарь и отправлять данные в DNS | Сохраняйте привязку к `127.0.0.1`; внешний доступ предоставляйте через HTTPS и авторизацию NGINX, описанные в [быстром старте](01_Quick_Start_RU.md) |
| Пароль PostgreSQL хранится открытым текстом в SQLite и её копиях | Чтение БД или резервной копии раскрывает пароль | Ограничьте права на БД и каталог копий; выделите отдельного пользователя PostgreSQL с минимальными правами |
| Нет автоматического удаления старых копий и ротации журнала | Каждый SQL-запрос изменения SQLite создаёт полную копию; каталог и журнал растут, заполнение диска блокирует изменения | Контролируйте свободное место и задайте собственные правила хранения копий и ротации журнала |
| Обычные копии SQLite создаются копированием файла | Копирование не гарантирует согласованную копию при одновременной записи; при включённом WAL данные из файла `-wal` не входят в такую копию | Для контрольных копий используйте штатный SQLite backup либо остановите SINVER перед файловым копированием. Миграционные копии создаются через SQLite backup |
| Запуск использует встроенный HTTP-сервер Flask | Нет отдельного сервера приложения, рассчитанного на промышленную эксплуатацию; NGINX сам по себе этого не меняет | Ограничьте нагрузку и число администраторов; до использования в продакшене разработайте и проверьте схему запуска и восстановления |
| Ключ браузерной сессии создаётся заново при запуске | Формы, открытые до перезапуска, отклоняются с `CSRF validation failed` и HTTP 400 | Обновите страницу после перезапуска. В обычной работе CSRF защищает отправку форм, но не заменяет авторизацию |

Изменения инвентаря не имеют журнала с указанием пользователя. Наличие копии SQLite помогает восстановить состояние, но не устанавливает, кто и почему его изменил.

## Инвентарь и формы

### Смена основного IP требует двух сохранений

Если у сервера уже есть **Primary = Yes**, создание второго основного IP или назначение другого существующего IP основным завершится HTTP 500. Операция нарушает ограничение «один основной IP» прежде, чем приложение снимает признак со старого адреса.

**Обход:** сначала откройте старый основной IP, установите **Primary = No** и сохраните. Затем назначьте **Primary = Yes** новому адресу. Между этими действиями у сервера временно нет основного IP; в этот момент не публикуйте DNS.

У сервера может быть только **один основной адрес суммарно для IPv4 и IPv6**. Для одновременной публикации обоих семейств создайте поддомены `A` и `AAAA` с одинаковым именем и свяжите каждый с подходящими адресами.

### Не все ошибки ввода объясняются в интерфейсе

Формат IP и соответствие семейству проверяются. Однако имена серверов, поддоменов и зон, числовой смысл параметров `SOA` и ряд других значений полностью не проверяются. Повтор уникального имени, адреса или другие нарушения ограничений БД обычно приводят к общей странице `Internal error` с HTTP 500.

Проверяйте данные до сохранения: имя сервера задавайте без основной зоны, поддомен — относительным именем или `@`, зону — доменным именем без пробелов; интервалы `SOA` — целыми числами секунд. После ошибки обновите страницу и проверьте фактическое состояние: некоторые составные изменения сохраняются несколькими отдельными запросами и не откатываются целиком.

Если существующая `SOA` в PowerDNS не содержит номер `SERIAL` после `MNAME` и `RNAME`, **Push** также возвращает HTTP 500 вместо пояснения. Проверьте поле `content` этой записи средствами PowerDNS/PostgreSQL и восстановите правильную структуру `MNAME RNAME SERIAL REFRESH RETRY EXPIRE MINIMUM`.

Например, имя сервера `app-01.infra.example.net` при основной зоне `infra.example.net` даст запись `app-01.infra.example.net.infra.example.net`. Для корректного результата достаточно `app-01`.

### Адреса IPv6 не приводятся к единому виду

Проверенный IP сохраняется в исходном текстовом виде. Эквивалентные IPv6, например `2001:db8::10` и `2001:0db8:0:0:0:0:0:10`, могут попасть в инвентарь как разные адреса. Используйте один, сокращённый формат записи IPv6 и перед добавлением проверяйте наличие адреса.

### Связи поддомена не ограничены семейством IP

В **Linked IP addresses** можно выбрать IPv6 для записи `A` или IPv4 для `AAAA`. Связь сохраняется и видна в интерфейсе, но соответствующая DNS-запись не формируется. Выбирайте IPv4 для `A`, IPv6 для `AAAA`; подробности — в [главе о поддоменах](06_Subdomains_RU.md).

### Фильтры и сортировка могут вводить в заблуждение

| Поведение | Последствие и обход |
| --- | --- |
| В фильтре **Roles** поле **Color** всегда отправляет выбранный цвет, по умолчанию `#8d7b68` | Поиск по имени одновременно ограничивается цветом, поэтому нужная роль может исчезнуть из результата. **Reset** показывает все роли; для поиска без цвета можно открыть `/roles?role_name=web`, заменив `web` искомым фрагментом |
| В списках выбранное значение **Sort by** не восстанавливается после отправки формы | Таблица сортируется по переданному параметру, а поле может показывать первый вариант. Перед следующим **Apply** заново выберите нужную сортировку |
| Текстовые фильтры используют шаблонный поиск | `%` означает любую последовательность символов, `_` — один символ. Учитывайте это при поиске имён с такими знаками |

## DNS

### SERIAL не гарантирует увеличение

Номер формируется по локальному времени с точностью до минуты в формате `YYMMDDhhmm`. Приложение сравнивает локальный и удалённый `SERIAL` на равенство, но не проверяет, что новый номер больше опубликованного. Повторное обновление за минуту может оставить номер прежним; перевод часов или смена часового пояса — уменьшить его. Вторичные DNS-серверы могут не принять обновление.

Установите для процесса SINVER единый часовой пояс, предпочтительно UTC, синхронизируйте часы и перед отправкой проверяйте **New SERIAL**. Если номер не увеличился, отложите отправку до следующей минуты. Если удалённый номер больше генерируемого, подготовьте отдельную процедуру смены `SERIAL` средствами DNS-сервера; простое редактирование локального поля не меняет алгоритм генерации.

### Подтверждённый план не проверяется повторно по данным зоны

Между **Push** и **Confirm apply** приложение не проверяет изменения записей или удалённого `SERIAL`; проверяется существование зоны и совпадение её идентификатора. Поэтому просмотренный план может стать устаревшим, если другой администратор или инструмент изменит DNS. Сходная ситуация возникает при изменении инвентаря после просмотра.

На время публикации согласуйте изменения зоны, подтверждайте план сразу после проверки и повторяйте **Push** после любых изменений. Не открывайте несколько планов одной зоны для последующего применения в произвольном порядке. Срок хранения плана — 10 минут — не гарантирует актуальность данных.

### PostgreSQL и SQLite обновляются раздельно

Транзакция PostgreSQL завершается раньше записи локального `SERIAL`. Если затем не удаётся создать копию SQLite или записать БД, DNS уже обновлён, а интерфейс может показать ошибку. Автоматического отката PostgreSQL в этом случае нет.

Проверьте свободное место и права на пути из конфигурации. После такой ошибки сверяйте `SOA` непосредственно в PowerDNS и приводите локальный `SERIAL` к фактическому значению; порядок описан в [главе DNS](10_DNS_RU.md#резервная-копия-и-восстановление).

### Сравнение некоторых существующих записей неточно

При предварительном сравнении имя записи приводится к нижнему регистру, пустой `TTL` — к `3600`, а пустые `disabled` и `auth` — к `false`. Удаление затем сравнивает сохранённые значения PostgreSQL напрямую. Поэтому строки с заглавными буквами в имени или `NULL` в перечисленных полях могут остаться после применения, хотя план показывал удаление. Также одинаковые существующие строки объединяются при сравнении и не очищаются, если уже совпадают с желаемой записью.

До первого применения проверьте данные PowerDNS: используйте имена в нижнем регистре, непустые значения `TTL`, `disabled`, `auth` и устраните дубликаты. После публикации проверяйте итоговые записи, особенно в БД, наполненной вручную.

### Синхронизация ограничена A, AAAA и SOA

SINVER не создаёт и не редактирует `NS`, `MX`, `TXT`, `CNAME`, `SRV`, `CAA` и другие типы через интерфейс. Он сохраняет такие строки при обновлении PowerDNS, однако `A`/`AAAA`, нужные для них, может удалить как отсутствующие в инвентаре. Например, сохранённая `NS` не защищает адрес DNS-сервера от удаления.

Внесите все необходимые адресные записи управляемой зоны в SINVER. Другие типы обслуживайте средствами DNS-сервера. Для DNSSEC и делегированных подзон отдельной обработки нет: новые записи получают `auth = true`, а корректировка DNSSEC-данных, очистка кеша и уведомления вторичных серверов не выполняются. Начальный сценарий руководства использует зону `NATIVE` без DNSSEC.

### Подключение PostgreSQL имеет ограниченные настройки

В интерфейсе нет отдельных полей для порта, политики TLS и проверенного сертификата сервера PostgreSQL. Для них действуют настройки клиента PostgreSQL и его окружения; ввод `host:port` в **PostgreSQL address** не заменяет отдельный параметр порта. Поэтому наличие защиты соединения из формы SINVER определить нельзя.

Начинайте с локального PostgreSQL на стандартном порту `5432`. Для удалённой БД настройте параметры клиента PostgreSQL и сетевой доступ отдельно, затем проверьте соединение от пользователя процесса SINVER. Чтение `SOA` в начале **Push** имеет таймаут подключения, но не задаёт лимит SQL-запроса: при блокировке этот этап может ждать дольше остальных.

Пустой пароль при редактировании зоны сохраняет прежний пароль. Через обычную форму удалить сохранённый пароль нельзя; используйте замену учётных данных или отдельную контролируемую процедуру изменения БД.

### Экспорт BIND9 требует подготовки

В скачанный файл не входят `NS` и другие типы, кроме `SOA`, `A`, `AAAA`; это не готовая замена существующей зоны. В `SOA` имена `MNAME` и `RNAME` переносятся дословно. Без завершающей точки BIND трактует их как относительные и добавляет имя зоны. Новый `SERIAL` попадает только в файл, в SQLite остаётся прежний.

Перед публикацией дополните файл нужными записями, исправьте абсолютные имена, проверьте увеличение номера и выполните `named-checkzone`, как показано в [главе DNS](10_DNS_RU.md#bind9).

## Режим обслуживания

Проверка схемы БД сравнивает её объявления с поставляемой схемой строго, игнорируя только пробелы и регистр. Даже функционально эквивалентная, но иначе записанная вручную схема может вызвать **Maintenance mode**. Не изменяйте схему SQL вне предусмотренной процедуры миграции. После ошибки изучите сообщение на странице, сохраните контрольную копию и исправьте причину; затем перезапустите SINVER.

Режим обслуживания блокирует основной интерфейс до успешной проверки. HTTP 503 в этом состоянии ожидаем; перезапуск без устранения причины проблему не решает. Само наличие сохранённой резервной копии не проверяет, что её восстановление подходит текущей версии и восстанавливает данные PowerDNS.
