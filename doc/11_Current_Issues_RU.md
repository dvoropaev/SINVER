# 11. Текущие проблемы

Глава описывает подтверждённые ошибки и ограничения **SINVER `0.0.0`**: условия их возникновения, последствия и доступные способы обхода.

## 11.1. Публикация DNS

### План может устареть до подтверждения

После **Push** SINVER сохраняет список изменений на 10 минут. При **Confirm apply** проверяется существование зоны и её ID, но **не проверяются повторно удалённый SERIAL, записи PowerDNS и текущие данные SINVER**.

Например, если после просмотра изменить основной IP, подтверждение всё равно опубликует прежний адрес. Если другой пользователь за это время изменит удалённую SOA, план может не удалить изменившуюся строку и добавить вторую SOA. Приложение при этом может сообщить об успехе; следующий Push остановится из-за двух SOA.

**Обход:** не меняйте данные между просмотром и подтверждением. Согласуйте публикацию с другими пользователями, используйте один актуальный просмотр и применяйте его сразу. После любого изменения заново нажимайте Push. Если SOA уже несколько, сначала исправьте зону средствами PowerDNS и проверьте её фактическое состояние.

### SERIAL не всегда увеличивается

Номер генерируется из локального времени хоста с точностью до минуты, без сравнения с прежним номером. Две публикации в одну минуту получают одинаковый SERIAL. Изменение системных часов или уже больший номер удалённой зоны могут дать меньший SERIAL.

Вторичные DNS-серверы могут не забрать изменённую зону, если её номер не стал новее. Даже обычная повторная публикация не гарантирует исправления.

**Обход:** перед подтверждением проверяйте New SERIAL и Remote SERIAL. Для последовательных обновлений дождитесь следующей минуты и создайте новый просмотр. Если новый номер всё ещё не подходит для обновления зоны, публикуйте её средствами PowerDNS с корректным SERIAL; генератор SINVER нельзя заменить параметром конфигурации. Простое изменение Local SERIAL не меняет алгоритм генерации.

### PowerDNS может обновиться до ошибки сохранения SQLite

Сначала фиксируются изменения PowerDNS, затем отдельной операцией обновляется локальный SERIAL. Если сохранение SQLite или создание её резервной копии не удалось, изменения PowerDNS уже остаются в силе, а SINVER может показать HTTP 500.

**Обход:** после такой ошибки сначала проверьте фактические записи и SOA PowerDNS. Устраните причину ошибки SQLite, приведите SERIAL карточки зоны к фактическому значению и сформируйте новый просмотр. Не повторяйте публикацию вслепую.

### Сравнение записей не исправляет некоторые данные PowerDNS

| Состояние записи PowerDNS | Недостаток | Что сделать |
| --- | --- | --- |
| Имя хранится с заглавными буквами | Просмотр сравнивает имена в нижнем регистре, а удаление ищет точное строковое совпадение. Исходная строка может остаться вместе с новой | Приведите имена записей к нижнему регистру средствами PowerDNS до публикации |
| В `ttl`, `disabled` или `auth` записано SQL `NULL` | Сравнение подставляет значения по умолчанию, но удаление не учитывает `NULL`. Ненужная строка может сохраниться | Проверьте и исправьте значения в базе PowerDNS; перед SQL-правкой сохраните её резервную копию |
| В базе есть полностью одинаковые строки | SINVER сравнивает наборы значений и не различает число одинаковых строк; лишние дубликаты могут остаться | Удалите дубликаты средствами администрирования PowerDNS и проверьте SOA |

После публикации проверяйте ответы DNS. Сообщение об успехе означает завершение запросов приложения, а не полную проверку корректности зоны.

## 11.2. Изменение серверов, адресов и связей

| Ошибка | Когда возникает и что происходит | Обход |
| --- | --- | --- |
| Новый основной IP нельзя назначить, пока выбран прежний | У сервера уже есть основной адрес, а другому назначают `Yes`, в том числе при создании или переносе IP. Ограничение уникальности срабатывает раньше снятия прежнего флага; результат — HTTP 500 | Сначала сохраните прежний адрес с `Primary = No`, затем новый с `Primary = Yes`. Порядок показан в [главе IP-адресов](05_IP_Addresses_RU.md) |
| Сохранение поддомена может завершиться частично | Поля карточки и отдельные изменения связей сохраняются раздельно. Если, например, выбранный IP удалили после открытия формы, возникает ошибка: часть изменений уже сохранена | После ошибки заново откройте карточку, проверьте имя, зону, тип и **весь набор IP**, затем сохраните актуальные связи |
| Адрес неподходящего семейства пропускается без предупреждения | К A можно привязать IPv6, к AAAA — IPv4. В карточке связь видна, но при формировании DNS такой адрес пропускается | Для A выбирайте только IPv4, для AAAA — только IPv6. Проверяйте DIFF перед публикацией |
| Эквивалентные IPv6 допускаются как разные адреса | Уникальность проверяется по введённой строке. Например, `2001:db8::10` и `2001:0db8:0:0:0:0:0:10` обозначают один адрес, но могут храниться раздельно | Используйте единую сокращённую запись в нижнем регистре и проверяйте каталог перед добавлением |

## 11.3. Проверка полей и сообщения об ошибках

SINVER проверяет формат IP при создании и разрешает в веб-форме поддомена только A/AAAA. При этом многие другие значения проверяются неполно:

- DNS-имена и параметры SOA не проверяются на правильный синтаксис. Например, текст вместо числа REFRESH сохраняется и попадает в SOA.
- При редактировании часть текстовых полей можно сохранить пустыми. Проверка `required` в форме создания не обеспечивает проверку всех последующих изменений.
- Уникальность, предельная длина и запрет удаления используемой основной зоны обрабатываются ограничениями SQLite. Их нарушение обычно выводит **Internal error (HTTP 500)** вместо сообщения с конкретным полем.
- Даты оплаты, адреса сайтов и цвета не имеют полноценной проверки на стороне SINVER. Ограничения браузерной формы не заменяют серверную проверку.

**Что делать:** используйте форматы из таблиц соответствующих глав, проверяйте уникальность имён и адресов до сохранения. Для зон вводите десятичные числа секунд и корректные MNAME/RNAME. После HTTP 500 проверьте карточку перед повторным сохранением: составная операция могла выполниться частично.

Режим `--debug` выводит подробности исключения прямо в HTML без безопасного экранирования текста ошибки. **Не включайте его для доступного другим пользователям интерфейса.** Для диагностики запускайте его только в контролируемом локальном сеансе и после проверки возвращайтесь к обычному запуску.

## 11.4. Недостатки интерфейса

| Недостаток | Влияние и обход |
| --- | --- |
| Поиск Roles дополнительно ограничивается цветом | Apply отправляет Color даже при поиске только по имени. Роли другого цвета исчезают из результата. Используйте Reset для полного списка или поиск без параметра `color`, как описано в [главе Roles](07_Roles_RU.md) |
| Sort by не сохраняет выбранный вариант на экране | Сортировка применяется, но после загрузки поле снова показывает первый вариант. Перед следующим Apply выберите нужный вариант заново; фактическое значение находится в параметре `sort` адресной строки |
| Связанные списки показывают `@.infra.example.net` | Это неверное отображение поддомена `@`. В сформированном DNS-имени используется правильное `infra.example.net`; проверяйте его во вкладке DNS |
| Нет очистки сохранённого пароля PostgreSQL | Пустое поле при Save оставляет прежний пароль. Через интерфейс можно заменить его, но нельзя удалить. Для перехода к подключению без пароля потребуется отдельная административная правка SQLite при остановленной службе и с резервной копией |
| Нет поиска по имени сервера, IP или поддомена, нет постраничного вывода | В больших каталогах навигация затруднена. Используйте имеющиеся фильтры и поиск браузера по отображаемой странице |
| Нет контроля одновременного редактирования карточки | Позднее сохранение старой формы может перезаписать чужие изменения. Перед правкой обновляйте карточку и согласуйте работу |

Сохранение открытой формы после перезапуска SINVER отклоняется защитой CSRF. Это штатное поведение: обновите страницу и повторите ввод; подробнее — в [главе о веб-интерфейсе](03_Web_Interface_RU.md).

## 11.5. Резервные копии и эксплуатация

### Автоматические копии не заменяют отдельное резервирование

Перед обычными изменениями SINVER копирует только основной файл SQLite файловой операцией. Это отличается от штатного SQLite backup API, используемого при миграции.

**Если база переведена в режим WAL, подтверждённые данные могут находиться в файле `-wal` и не попасть в автоматическую `.bak`-копию.** При одновременной записи другим процессом обычное файловое копирование также не гарантирует согласованного снимка. Режим WAL SINVER самостоятельно не включает.

**Обход:** не включайте WAL в расчёте на автоматические копии SINVER. Для надёжного резервирования используйте SQLite `.backup`/backup API либо остановите все процессы записи перед файловым копированием. Периодически проверяйте копию командой `PRAGMA integrity_check` и пробным восстановлением. Пример согласованной копии и порядок восстановления приведены в [конфигурации](02_Configuration_RU.md).

Копия создаётся перед отдельными операциями записи, поэтому одна форма может породить несколько файлов. Автоматического удаления старых копий и ротации файла журнала нет. Контролируйте свободное место и настройте срок хранения средствами ОС. Если каталог копий недоступен или диск заполнен, изменения данных могут блокироваться. Эти копии **не резервируют PostgreSQL PowerDNS**: для него требуется отдельный backup.

### Доступ и запуск

В приложении нет учётных записей, уровней доступа и истории изменений с указанием пользователя. Все допущенные к SINVER пользователи получают одинаковые возможности.

Запуск использует встроенный сервер Flask; поддерживаемой конфигурации производственного WSGI-сервера в проекте нет. NGINX обеспечивает HTTPS и проверку входа, но не меняет способ запуска SINVER. Оставляйте SINVER на `127.0.0.1` и ограничьте доступ к его файлам. Если нужен доступ извне, настройте NGINX с HTTPS и проверкой входа по [инструкции установки](01_Quick_Start_RU.md).

Не определяйте готовность только по строке журнала `SINVER started successfully`: она выводится и при заблокированном основном интерфейсе. Проверьте страницу и статус HTTP; `Maintenance mode` возвращает 503.

## 11.6. Функциональные ограничения

| Ограничение | Практическое следствие |
| --- | --- |
| Через SINVER создаются A, AAAA и SOA | NS, MX, TXT, CNAME, SRV, CAA и другие типы обслуживаются отдельно. При Push существующие записи этих других типов сохраняются |
| Нет импорта действующей зоны | Перед первой публикацией вручную внесите нужные A/AAAA в SINVER: отсутствующие записи управляемых типов планируется удалить |
| TTL публикации фиксирован: 3600 секунд | Индивидуальный TTL не задаётся; запись с другим TTL заменяется при синхронизации |
| Один Primary на сервер | Для одного имени с IPv4 и IPv6 добавьте вторую запись через поддомен; пример есть в [главе IP-адресов](05_IP_Addresses_RU.md) |
| BIND-экспорт содержит только SOA и адресные записи | Результат требует дополнения NS и другими нужными записями, проверки и ручной установки; готовый порядок — в [главе DNS](10_DNS_RU.md) |
| Нет управления делегацией, уведомлениями вторичных серверов и DNSSEC | Синхронизация меняет строки базы. Настраивайте делегацию, репликацию и обслуживание подписанных зон отдельно; быстрый старт использует обычную неподписанную зону типа NATIVE |
| Нет проверки доступности серверов и контроля оплат | Несколько IP у имени не обеспечивают автоматическое исключение отказавшего сервера; Paid until — справочная дата без напоминаний |
