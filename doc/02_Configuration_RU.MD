# 2. Конфигурация

[Содержание](README_RU.md) · [Назад: Быстрый старт](01_Quick_Start_RU.MD) · [Далее: Веб-интерфейс](03_Web_Interface_RU.MD)

## 2.1. Файл настроек

Правильное имя файла — **`sinver.toml`**. Это файл формата [TOML](https://toml.io/): каждый параметр записывается как `имя = значение`, строки заключаются в кавычки, комментарии начинаются с `#`.

Установленная служба читает `/etc/sinver.toml`. Файл `sinver.toml` в репозитории — образец для установки; изменение образца не меняет уже работающую службу. Другой файл можно указать через `--config`.

Полная стандартная конфигурация:

```toml
database_path = "/var/lib/sinver/sinver.sqlite"
database_backup_path = "/var/lib/sinver/backups"
http_addr = "127.0.0.1"
http_port = 8080
log_file = "/var/log/sinver/sinver.log"
```

Все настройки находятся на верхнем уровне файла: секции вида `[server]` не нужны. Неизвестные имена параметров игнорируются; опечатка в обязательном параметре приводит к ошибке запуска.

## 2.2. Параметры

| Параметр | Тип и обязательность | Значение образца / значение по умолчанию | Назначение и требования |
| --- | --- | --- | --- |
| `database_path` | Непустая строка, **обязателен** | Образец: `/var/lib/sinver/sinver.sqlite`. Значения по умолчанию нет | Путь к файлу SQLite, где хранятся зоны, серверы, адреса и другие объекты. При отсутствии файла SINVER создаёт новую базу; существующую проверяет при запуске. Учётной записи процесса нужны чтение и запись файла, а также запись в каталог для служебных файлов SQLite |
| `database_backup_path` | Непустая строка, **обязателен** | Образец: `/var/lib/sinver/backups`. Значения по умолчанию нет | Каталог автоматических резервных копий SQLite. Должен быть доступен процессу на запись. Не указывайте имя файла |
| `http_addr` | Непустая строка, необязателен | По умолчанию `127.0.0.1` | Адрес прослушивания HTTP. `127.0.0.1` допускает доступ с этого узла и через локальный reverse proxy/SSH-туннель. `0.0.0.0` открывает все IPv4-интерфейсы и предоставляет прямой доступ к приложению без встроенной проверки пользователя. Для схемы с NGINX сохраните loopback |
| `http_port` | Целое число **без кавычек**, необязателен | По умолчанию `8080` | TCP-порт HTTP, допустимы значения `1`–`65535`. Числа с дробной частью, строки и логические значения отклоняются. Для стандартной непривилегированной службы используйте свободный порт `1024` или выше |
| `log_file` | Непустая строка, **обязателен** | Образец: `/var/log/sinver/sinver.log`. Значения по умолчанию нет | Файл журнала в UTF-8. Родительский каталог создаётся при настройке логирования, если права позволяют. Процессу необходимы права на добавление в файл и создание его каталога |

**Параметры подключения к PostgreSQL задаются отдельно для каждой зоны во вкладке Zones.** В `sinver.toml` нет настроек PostgreSQL, TLS, пользователей, TTL, срока хранения резервных копий или уровня логирования. Поля зоны описаны в главе [«Зоны»](09_Zones_RU.MD).

## 2.3. Разрешение путей

Абсолютный путь используется непосредственно. Относительный путь считается **от каталога выбранного конфигурационного файла**, а не от текущего каталога терминала.

Например, для файла `/srv/sinver/config/sinver.toml`:

```toml
database_path = "../data/sinver.sqlite"
database_backup_path = "../backups"
log_file = "../logs/sinver.log"
```

получаются пути `/srv/sinver/data/sinver.sqlite`, `/srv/sinver/backups` и `/srv/sinver/logs/sinver.log`.

Поддерживается `~` — домашний каталог пользователя **процесса SINVER**. Переменные среды, например `$HOME`, не подставляются. Для службы удобнее использовать абсолютные пути.

**Изменение `database_path` не переносит данные.** Если новый файл отсутствует, SINVER создаст пустую базу. Для переноса остановите службу, скопируйте действующую базу в новый путь, обеспечьте права и только затем измените конфигурацию.

## 2.4. Владельцы и доступ к файлам

Стандартный unit запускает процесс с `User=sinver`, `Group=sinver`, `UMask=0077`. Установщик выставляет:

| Объект | Владелец | Права |
| --- | --- | --- |
| `/etc/sinver.toml` | `root:sinver` | `0640` — root изменяет, служба читает |
| `/var/lib/sinver`, `/var/log/sinver` | `sinver:sinver` | `0750` |
| `/var/lib/sinver/backups` и подкаталоги | `sinver:sinver` | `0700` |
| Файлы базы, копий и журналов в стандартных каталогах | `sinver:sinver` | `0600` |
| Программа, схема и миграции | `root:root` | Служба может читать, но не изменять |

SQLite и её копии содержат пароли PostgreSQL из карточек зон в открытом виде. Ограничивайте доступ к этим файлам и используйте пользователя `sinver` только для службы SINVER.

При нестандартных путях создайте каталоги до запуска. Например:

```bash
sudo install -d -o sinver -g sinver -m 0750 /srv/sinver/data /srv/sinver/logs
sudo install -d -o sinver -g sinver -m 0700 /srv/sinver/backups
```

Пользователю `sinver` также нужен доступ на проход через все родительские каталоги. На существующей базе задайте владельца `sinver:sinver` и права `0600`.

Unit использует `ProtectSystem=full`, поэтому запись в `/usr`, `/boot` и `/etc` внутри службы запрещена. **Не размещайте изменяемую базу, её копии или журнал в этих каталогах.** Привилегированные порты также не подходят для стандартной службы; HTTPS обслуживает NGINX.

## 2.5. Изменение конфигурации и управление службой

Настройки читаются один раз при запуске. После редактирования выполните:

```bash
sudoedit /etc/sinver.toml
sudo systemctl restart sinver.service
sudo systemctl status sinver.service --no-pager
```

При изменении только TOML команда `systemctl daemon-reload` не требуется. Она нужна при изменении unit-файла или его drop-in-конфигурации.

| Действие | Команда |
| --- | --- |
| Запустить | `sudo systemctl start sinver.service` |
| Остановить | `sudo systemctl stop sinver.service` |
| Запускать при загрузке ОС | `sudo systemctl enable sinver.service` |
| Отключить автоматический запуск | `sudo systemctl disable sinver.service` |
| Журнал systemd | `sudo journalctl -u sinver.service -n 100 --no-pager` |
| Журнал приложения | `sudo tail -n 100 /var/log/sinver/sinver.log` |

После каждого перезапуска обновите открытые страницы в браузере: ключ подписания сессии создаётся заново, поэтому отправка старой формы может дать HTTP 400 из-за CSRF.

Ошибки чтения TOML и настройки файла журнала завершают запуск с кодом `1`. Ошибка проверки существующей SQLite-базы переводит веб-интерфейс в **Maintenance mode**. Причину ищите в журналах; порядок работы с этим экраном описан в главе [«веб-интерфейс»](03_Web_Interface_RU.MD).

Если требуется другой файл конфигурации для systemd, создайте override через `sudo systemctl edit sinver.service`:

```ini
[Service]
ExecStart=
ExecStart=/usr/bin/sinver --config /srv/sinver/config/sinver.toml
```

Пустая строка `ExecStart=` сбрасывает прежнюю команду. Обеспечьте чтение нового конфигурационного файла пользователем `sinver`, затем выполните `sudo systemctl daemon-reload` и `sudo systemctl restart sinver.service`.

## 2.6. Параметры командной строки

| Параметр | Действие |
| --- | --- |
| `--config ПУТЬ` | Выбрать TOML-файл. Без параметра используется `/etc/sinver.toml` |
| `--debug` | Показывать текст неожиданной ошибки на странице `Debug error`. Не включает интерактивный отладчик Flask и автоматический перезапуск кода |
| `--init-if-missing` | Флаг совместимости. Отсутствующая база создаётся автоматически и без этого флага |
| `-h`, `--help` | Показать справку и завершить работу |

Пример ручного запуска установленной программы:

```bash
sudo systemctl stop sinver.service
sudo -u sinver sh -c 'umask 0077; exec /usr/bin/sinver --config /etc/sinver.toml'
```

Процесс работает в переднем плане; для завершения нажмите `Ctrl+C`, затем при необходимости снова запустите службу systemd. Два экземпляра на одном порту запустить нельзя.

Временно используйте `--debug` только при диагностике с ограниченным доступом: текст исключения может содержать внутренние данные. В штатной эксплуатации оставляйте его выключенным.

## 2.7. Резервные копии и журналы

При обычных изменениях собственной базы SINVER перед SQL-операцией создаёт копию SQLite в `database_backup_path`. Имя имеет вид:

```text
sinver.sqlite.YYYYMMDD_HHMMSS_microseconds.bak
```

Одно действие интерфейса может выполнять несколько SQL-операций и создавать несколько копий. При обслуживании и миграции базы копия также сохраняется перед изменением. Копии автоматически не удаляются. Планируйте свободное место, перенос копий на другой носитель и удаление устаревших по своей политике хранения.

**Эти файлы сохраняют данные SINVER, а не PostgreSQL PowerDNS.** При восстановлении старой SQLite-копии DNS-записи автоматически не откатываются. После восстановления проверьте SERIAL и сравните план следующей отправки с действующим DNS.

Текущая реализация обычных копий использует копирование файла, а не SQLite Backup API. При параллельных изменениях и при стороннем включении WAL такая копия может быть неполной. Для контрольной копии остановите SINVER и все другие процессы записи в эту базу, затем выполните `.backup` и проверку:

```bash
sudo systemctl stop sinver.service
sudo -u sinver sh -c 'umask 0077; exec sqlite3 -readonly /var/lib/sinver/sinver.sqlite ".backup /var/lib/sinver/backups/sinver.sqlite.manual.bak"'
sudo -u sinver sqlite3 -readonly /var/lib/sinver/backups/sinver.sqlite.manual.bak 'PRAGMA integrity_check; PRAGMA foreign_key_check;'
sudo systemctl start sinver.service
```

Выбирайте новое имя вместо `sinver.sqlite.manual.bak`, чтобы сохранить предыдущую копию. `.backup` использует SQLite Backup API. Проверка должна вывести `ok` и не вывести нарушений внешних ключей. Флаг `-readonly` запрещает создание отсутствующего файла базы при опечатке в пути.

Журнал приложения ведётся на уровне `INFO`, содержит запуск и этапы публикации PowerDNS. Отдельные сообщения обслуживания и сообщения HTTP-сервера попадают в journal systemd. Встроенной ротации файла журнала нет; настройте её внешними средствами. Поскольку приложение держит файл открытым, при ротации с переименованием нужен перезапуск службы для открытия нового файла.

## 2.8. Восстановление SQLite

Восстанавливайте базу при остановленной службе и отсутствии других процессов записи в неё. Ниже используются стандартные пути; `REPLACE_WITH_BACKUP.bak` необходимо заменить выбранным именем файла.

1. Остановите SINVER и проверьте копию:

   ```bash
   sudo systemctl stop sinver.service
   sudo -u sinver sqlite3 -readonly /var/lib/sinver/backups/REPLACE_WITH_BACKUP.bak 'PRAGMA integrity_check; PRAGMA foreign_key_check;'
   ```

   Ожидается строка `ok` и отсутствие строк с нарушениями внешних ключей. Если проверка не прошла, не устанавливайте эту копию; выберите и проверьте другую.

2. Сохраните текущую базу под новым именем перед заменой:

   ```bash
   sudo -u sinver sh -c 'umask 0077; exec sqlite3 -readonly /var/lib/sinver/sinver.sqlite ".backup /var/lib/sinver/backups/sinver.sqlite.before-restore.bak"'
   ```

3. Установите выбранную копию как действующую базу:

   ```bash
   sudo install -o sinver -g sinver -m 0600 /var/lib/sinver/backups/REPLACE_WITH_BACKUP.bak /var/lib/sinver/sinver.sqlite
   sudo systemctl start sinver.service
   sudo systemctl status sinver.service --no-pager
   ```

4. Откройте интерфейс и проверьте объекты и журналы. При запуске SINVER проверит соответствие схемы и версии базы. Если включён Maintenance mode, выясните причину до следующих изменений.

Этот пример рассчитан на стандартный режим SQLite текущего приложения. Не заменяйте файлы работающей базы и не удаляйте её служебные файлы для обхода ошибки. Если обнаружены `-wal`, `-shm` или незавершённый journal от других процессов, сначала завершите или восстановите их средствами SQLite.

Ограничения резервных копий и публикации DNS разобраны в главе [«Текущие проблемы»](11_Current_Issues_RU.MD).
