# 10. DNS — публикация записей

[Содержание](README_RU.md) · [Назад: Зоны](09_Zones_RU.MD) · [Далее: Текущие проблемы](11_Current_Issues_RU.MD)

Вкладка **DNS** формирует DNS-записи из инвентаризации SINVER и предлагает два способа передачи: применить изменения в PostgreSQL PowerDNS или скачать файл зоны для BIND. В обоих случаях обрабатывается одна выбранная зона.

## 10.1. Какие данные попадают в DNS

| Источник | Результат |
| --- | --- |
| Параметры зоны из [Zones](09_Zones_RU.MD) | Одна SOA-запись зоны с новым SERIAL |
| Основная зона сервера и его IP с флагом **Primary** | `hostname.zone A IPv4` либо `hostname.zone AAAA IPv6` |
| Поддомен типа `A` и связанные IPv4-адреса | По одной A-записи на каждый подходящий IP |
| Поддомен типа `AAAA` и связанные IPv6-адреса | По одной AAAA-записи на каждый подходящий IP |
| Поддомен с именем `@` | Запись на имя самой зоны, например `example.net A 192.0.2.10` |

IP без флага **Primary** не формирует основное имя сервера, но может использоваться в поддоменах. Сервер без основной зоны не создаёт основную DNS-запись. Поддомен без связанных IP или с IP неподходящего семейства не создаёт запись: для `A` нужны IPv4, для `AAAA` — IPv6. Роли, цвета, хостинги и описания в DNS не передаются.

У сервера допускается один **Primary** на оба семейства адресов. Для публикации основного имени одновременно в IPv4 и IPv6 создайте дополнительный поддомен с тем же именем, что и `hostname`, и типом второго семейства. Например, у `web01` основной IPv4 `192.0.2.10`; поддомен `web01` типа `AAAA` со связью на `2001:db8::10` добавит `web01.example.net AAAA 2001:db8::10`.

## 10.2. Элементы вкладки

| Элемент | Назначение |
| --- | --- |
| **PowerDNS + PostgreSQL → Zone** | Зона для сравнения и применения изменений в PowerDNS |
| **Push** | Чтение PowerDNS и подготовка предварительного просмотра; сам по себе DNS не изменяет |
| **Bind9 → Zone** | Зона для скачивания файла BIND |
| **Generate config** | Скачать файл `<имя_зоны>.db` |
| **Remote SERIAL** | SERIAL прочитанной SOA в PowerDNS |
| **Local SERIAL** | SERIAL, сохранённый в SQLite SINVER |
| **New SERIAL** | SERIAL, подготовленный для этой публикации |
| **Все равно продолжить** | Подтвердить продолжение подготовки при несовпадении локального и удалённого SERIAL |
| **SQL preview** | Запросы удаления и добавления, соответствующие подготовленным изменениям |
| **Confirm apply** | Применить подготовленные изменения после подтверждения браузера |

При открытии вкладки автоматически выбирается первая зона по имени, если переход не указал конкретную зону. У форм PowerDNS и BIND отдельные выпадающие списки: перед действием проверяйте выбор в нужной форме. Фильтров и настройки сортировки на вкладке DNS нет.

## 10.3. Публикация в PowerDNS

### Условия работы

PowerDNS должен использовать PostgreSQL. SINVER подключается непосредственно к его базе, а не к HTTP API. Должны быть установлены Python-драйвер `psycopg2`, настроены поля подключения зоны и права пользователя; подготовка описана в [Быстром старте](01_Quick_Start_RU.MD).

В таблице PowerDNS `domains` должна существовать строка, где `name` точно равно имени зоны SINVER. Для её `domain_id` в `records` должна быть **ровно одна SOA-запись**. Если зоны нет, SOA отсутствует или их несколько, предварительный просмотр остановится с ошибкой. SINVER не создаёт строку `domains` и не исправляет начальную SOA автоматически.

> **SINVER управляет всеми A, AAAA и SOA выбранной зоны.** План включает удаление записей этих типов, которых нет в сформированном списке инвентаризации. Существующие записи других типов, например NS, MX, TXT, CNAME и CAA, сохраняются. До первой публикации внесите в SINVER все A и AAAA, которые требуется оставить, включая адреса DNS-серверов внутри этой зоны.

В текущей версии записи с заглавными буквами в имени или `NULL` в TTL/флагах могут не удалиться, а существующие точные дубликаты могут остаться. До первой публикации проверьте такие данные; объяснение и обход — в [текущих проблемах](11_Current_Issues_RU.MD).

### Порядок действий

1. Выберите зону в **PowerDNS + PostgreSQL** и нажмите **Push**. SINVER читает удалённую SOA, извлекает её SERIAL и сравнивает его с локальным.
2. Если SERIAL различаются, появится предупреждение `Local SERIAL is out of sync with Remote SERIAL.`. Полный DIFF ещё не сформирован. Сначала установите причину расхождения: удалённую зону могли изменить вручную или через другую программу. Кнопка **Все равно продолжить** разрешает повторно прочитать данные и подготовить изменения, но не применяет их.
3. Сравните **Remote SERIAL**, **Local SERIAL**, **New SERIAL**, список изменений и **SQL preview**.
4. Нажмите **Confirm apply** и подтвердите действие в диалоге браузера.
5. При успехе появляется `PowerDNS update applied and local serial updated.`. PostgreSQL уже обновлён, а SERIAL зоны в SQLite установлен в **New SERIAL**. Проверьте ответы авторитетного DNS-сервера, например:

   ```bash
   dig @192.0.2.53 example.net SOA +short
   dig @192.0.2.53 web01.example.net A +short
   dig @192.0.2.53 api.example.net AAAA +short
   ```

Адрес `192.0.2.53` в проверке — пример адреса вашего DNS-сервера. Все адреса `192.0.2.0/24` и `2001:db8::/32` в руководстве служат для примеров; в рабочей установке замените их реальными.

Нажатие **Все равно продолжить** разрешает расхождение SERIAL только при подготовке нового просмотра. Оно не выполняет слияние данных и не сохраняет отсутствующие в SINVER записи управляемых типов.

### Чтение DIFF

Строка просмотра имеет формат:

```text
знак name | type | content | ttl | disabled | auth
```

| Часть | Значение |
| --- | --- |
| `+` / `-` | Добавление / удаление строки `records` |
| `name` | Полное доменное имя; при сравнении SINVER приводит его к нижнему регистру |
| `type` | `A`, `AAAA` или `SOA` |
| `content` | IP-адрес либо семь полей SOA: `MNAME RNAME SERIAL REFRESH RETRY EXPIRE MINIMUM` |
| `ttl` | TTL записи в секундах |
| `disabled` | Признак выключенной записи PowerDNS: `True` / `False` |
| `auth` | Признак авторитетной записи PowerDNS: `True` / `False` |

Все создаваемые строки имеют `ttl = 3600`, `disabled = False`, `auth = True`. Изменение TTL, флагов или содержимого представлено удалением прежней строки и добавлением новой. Поэтому существующая A-запись с TTL `300` будет заменена строкой с TTL `3600`, даже если имя и IP не изменились. Точные совпадения не обновляются. Другие поля таблицы PowerDNS `records` в сравнении не участвуют и при вставке получают значения по умолчанию её схемы.

Например, поддомен `api` типа `A`, связанный с `192.0.2.10`, добавит:

```text
+ api.example.net | A | 192.0.2.10 | 3600 | False | True
```

Изменение SERIAL обычно добавляет новую SOA и удаляет прежнюю. В **SQL preview** сначала перечислены удаления, затем вставки. Приложение применяет сохранённый план параметризованными запросами; копировать и выполнять текст просмотра вручную не требуется.

### Срок действия просмотра и ошибки применения

Подготовленный план хранится в памяти процесса **10 минут** и используется один раз. Перезапуск SINVER удаляет планы. Если срок истёк, план уже использован или попытка применения завершилась ошибкой, снова нажмите **Push**, заново проверьте DIFF и подтвердите новый план. Сообщение `Preview is expired. Please run push again and confirm apply.` означает, что применимого плана больше нет.

При применении SINVER повторно находит зону в `domains` и проверяет, что её ID соответствует плану. **Он не перепроверяет SERIAL, записи PowerDNS и инвентаризацию после просмотра.** Не изменяйте данные зоны между **Push** и **Confirm apply**; при любом изменении формируйте новый просмотр. Для общей базы согласуйте публикацию с другими администраторами. Отдельной блокировки зоны на время просмотра нет.

Удаления и вставки в PostgreSQL выполняются в одной транзакции. Если запрос завершается ошибкой, изменения этой транзакции откатываются. Ограничения времени: подключение — 5 секунд, ожидание блокировки — 5 секунд, выполнение отдельного SQL-запроса — 30 секунд, простой открытой транзакции — 30 секунд. Это не общий лимит времени всей операции; первичное чтение `domains` и SOA при просмотре не имеет лимита SQL-запроса, заданного SINVER.

После успешной фиксации PostgreSQL локальный SERIAL обновляется отдельной операцией SQLite. Ошибка SQLite на этом этапе не откатывает PostgreSQL: сравните фактическую SOA с карточкой зоны и восстановите согласованность данных перед новым просмотром.

### Сценарии публикации

| Сценарий | Действия и результат |
| --- | --- |
| Первое имя сервера | Для `web01` выберите основную зону `example.net` и Primary IPv4 `192.0.2.10`; появится `web01.example.net A 192.0.2.10` |
| Имя приложения в обоих семействах | Создайте два поддомена `api`: `A` → `192.0.2.10` и `AAAA` → `2001:db8::10`; появятся обе записи `api.example.net` |
| Несколько адресов приложения | Свяжите один поддомен с несколькими IP подходящего семейства; каждый IP образует отдельную DNS-запись |
| Адрес самой зоны | Создайте поддомен `@` типа `A` и свяжите с IPv4; появится `example.net A <IP>` |
| Замена IP приложения | Измените связи поддомена и сформируйте новый просмотр: появятся добавление нового адреса и удаление прежнего, если его больше не формирует другой поддомен или Primary сервера |
| Удаление имени | Удалите поддомен или его связи и сформируйте новый просмотр: соответствующие A/AAAA попадут в удаление, если это же имя с тем же адресом больше не формируется другим источником |

Список формируется совместно из основных имён серверов и поддоменов. Если поддомен повторяет имя сервера, его адреса объединяются с адресом основного имени; это не переопределение. В PowerDNS точные дубликаты ожидаемых строк объединяются. Проверьте DIFF, чтобы случайное совпадение имён не направило запросы на лишний сервер.

> **Пустая или неполная инвентаризация может удалить рабочие записи.** Если у зоны нет подходящих Primary IP и связанных поддоменов, ожидаемый список содержит только SOA. Применение такого плана удаляет все существующие A и AAAA зоны. Неподходящее семейство связанного IP также может привести к отсутствию ожидаемой записи и её удалению.

## 10.4. SERIAL

SINVER генерирует SERIAL во время подготовки просмотра PowerDNS или файла BIND в формате `YYMMDDhhmm`: год из двух цифр, месяц, день, час и минута. Время берётся **в локальном часовом поясе хоста SINVER**. Например, `2610071200` означает 7 октября 2026 года, 12:00 по времени этого хоста.

При успешном применении PowerDNS SERIAL сохраняется в SQLite. При просмотре, отказе от подтверждения или экспорте BIND локальное значение не меняется.

Генератор не учитывает предыдущее значение и не гарантирует увеличение SERIAL. Две публикации за одну минуту могут получить одинаковый номер; после изменения часов или при большем удалённом номере новый SERIAL может оказаться меньше. Перед применением проверяйте **New SERIAL**, особенно если используются вторичные DNS-серверы. Последствия и ограничения разобраны в главе [Текущие проблемы](11_Current_Issues_RU.MD).

## 10.5. Экспорт BIND

1. Выберите зону в блоке **Bind9**.
2. Нажмите **Generate config**. Браузер скачает, например, `example.net.db`.
3. Проверьте и дополните файл, затем опубликуйте его на BIND вручную.

Файл содержит `$TTL 3600`, SOA с новым SERIAL и сформированные A/AAAA. Имена A/AAAA записываются полностью с завершающей точкой. При наличии основной записи `web01` и двух поддоменов `api` результат выглядит так:

```bind
$TTL 3600
@ IN SOA ns1.example.net. hostmaster.example.net. (2610071200 3600 600 1209600 300)
api.example.net. IN A 192.0.2.10
api.example.net. IN AAAA 2001:db8::10
web01.example.net. IN A 192.0.2.10
```

SERIAL в примере условный; в скачанном файле будет время генерации. Файл не содержит `$ORIGIN`: имя зоны передаёт конфигурация BIND или аргумент утилиты проверки.

**Экспорт не добавляет NS, MX, TXT, CNAME и другие типы записей.** Для полноценной зоны нужны как минимум NS; при DNS-сервере внутри зоны также нужны его адресные записи. Например, дополните файл:

```bind
@ IN NS ns1.example.net.
ns1.example.net. IN A 192.0.2.53
```

При обновлении существующей зоны перенесите в новый файл необходимые записи других типов и настройки. Полная замена прежнего файла только результатом SINVER потеряет эти записи.

Проверка подготовленного файла:

```bash
named-checkzone example.net ./example.net.db
```

После успешной проверки установите файл в путь, заданный для зоны в конфигурации BIND, проверьте владельца и права, выполните `rndc reload example.net` и проверьте ответы через `dig`. SINVER не изменяет `named.conf`, не переносит файл на DNS-сервер и не перезагружает BIND. **SERIAL в SQLite при экспорте остаётся прежним**: повторный переход к PowerDNS может показать расхождение.

Текущие ограничения синхронизации, проверки данных и экспорта описаны в главе [Текущие проблемы](11_Current_Issues_RU.MD).
