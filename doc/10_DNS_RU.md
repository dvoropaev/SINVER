# 10. DNS

[← Назад](09_Zones_RU.md) · [Содержание](README_RU.md#содержание) · [Вперёд →](11_Current_Issues_RU.md)

Вкладка **DNS** публикует данные выбранной зоны в PostgreSQL, используемую PowerDNS, или скачивает файл зоны для BIND9. Изменения на вкладках **Servers**, **IP addresses**, **Subdomains** и **Zones** сами по себе DNS не обновляют.

## Какие записи формирует SINVER

| Источник | Результат |
| --- | --- |
| Сервер с **Primary zone** и IP с **Primary = Yes** | `A` для основного IPv4 либо `AAAA` для основного IPv6: `<hostname>.<zone>` |
| Поддомен `A` со связанными IPv4 | По одной записи на каждый связанный IPv4 |
| Поддомен `AAAA` со связанными IPv6 | По одной записи на каждый связанный IPv6 |
| Поддомен с именем `@` | Запись на имя самой зоны, например `infra.example.net` |
| Параметры зоны | Одна запись `SOA` с новым `SERIAL` |

IP без признака **Primary** публикуется только через явно связанный поддомен. Сервер без основной зоны не создаёт автоматическую запись. Поддомен без IP подходящего семейства не создаёт записей. Роли, хостинги и описания на DNS не влияют.

Для публикуемых записей установлены `TTL = 3600` секунд, `disabled = false` и `auth = true`. В интерфейсе эти значения изменить нельзя. `TTL` определяет время хранения ответа в DNS-кеше; `disabled` управляет отключением записи в PowerDNS; `auth` — признаком авторитетной записи.

> **Важно:** при отправке в PowerDNS SINVER управляет **всеми `A`, `AAAA` и `SOA` выбранной зоны**. Такие записи, отсутствующие в сформированном списке, попадут в удаление. До первой отправки внесите в SINVER все нужные адресные записи, включая адреса серверов имён. Записи других типов, в том числе `NS`, `MX`, `TXT` и `CNAME`, сохраняются в PowerDNS.

## PowerDNS + PostgreSQL

SINVER подключается непосредственно к БД PostgreSQL; API PowerDNS не используется. Зона должна уже существовать в таблице `domains` и иметь ровно одну запись `SOA` в `records`. Создание зоны в SINVER не создаёт её в PowerDNS. Подключение задаётся в [карточке зоны](09_Zones_RU.md); подготовка PowerDNS описана в [быстром старте](01_Quick_Start_RU.md).

### Поля и кнопки

| Элемент | Назначение |
| --- | --- |
| **Zone** | Выбор одной зарегистрированной в SINVER зоны для отправки |
| **Push** | Чтение данных из PostgreSQL и подготовка предварительного просмотра; БД PowerDNS ещё не изменяется |
| **Remote SERIAL** | Номер версии из текущей `SOA` в PowerDNS |
| **Local SERIAL** | Значение `SERIAL`, сохранённое в SINVER |
| **New SERIAL** | Номер, который будет записан при подтверждении |
| Список изменений | Строки `+` будут добавлены, строки `-` будут удалены |
| **SQL preview** | Читаемое представление планируемых SQL-операций; вручную выполнять его не требуется |
| **Все равно продолжить** | При несовпадении номеров версий разрешает заново подготовить план, несмотря на предупреждение |
| **Confirm apply** | Применение показанного плана после подтверждения в диалоге браузера |

Строка списка изменений имеет порядок `имя | тип | значение | TTL | disabled | auth`. Например:

```text
+ app-01.infra.example.net | A | 192.0.2.10 | 3600 | False | True
```

### Порядок отправки

1. Убедитесь, что инвентарь содержит все нужные `A` и `AAAA` выбранной зоны. Перед первой отправкой сохраните резервную копию БД PowerDNS.
2. Выберите **Zone = infra.example.net**, нажмите **Push**.
3. Если номера `SERIAL` различаются, выясните причину. Так бывает после изменения зоны другим инструментом или восстановления резервной копии. Нажимайте **Все равно продолжить**, только когда данные SINVER готовы заменить адресные записи этой зоны.
4. Проверьте список изменений и `SQL preview`. Особое внимание уделите строкам `-`, адресам серверов имён и параметрам `SOA`.
5. Нажмите **Confirm apply** и подтвердите `Apply update to PowerDNS?` в браузере. Отмена диалога оставляет PostgreSQL без изменений.
6. Дождитесь сообщения `PowerDNS update applied and local serial updated.` Затем проверьте ответы DNS.

Для сценария с `app-01` создайте сервер с основной зоной `infra.example.net` и адресом `192.0.2.10`, отмеченным **Primary = Yes**. Если адрес DNS-сервера `ns1.infra.example.net` — `192.0.2.53`, внесите его в инвентарь отдельным сервером `ns1` с основным адресом: иначе его существующая `A`-запись попадёт в удаление. Сохранённая `NS`-запись сама по себе адрес `ns1` не защищает.

План хранится в памяти SINVER **10 минут**, действует один раз и пропадает после перезапуска приложения. Если появились `Preview is expired. Please run push again and confirm apply.` или ошибка применения, нажмите **Push** повторно и проверьте новый план. Не меняйте инвентарь или зону PowerDNS между просмотром и подтверждением: план автоматически не пересчитывается.

### Что меняется в PostgreSQL

SINVER сравнивает записи по имени, типу, значению, `TTL`, `disabled` и `auth`. Изменение любого из этих полей представляется удалением старой и добавлением новой записи. Совпадающие записи сохраняются; одинаковые записи из разных источников SINVER объединяются. В таблицу `domains` приложение ничего не записывает. Другие зоны не участвуют в плане.

Удаления и добавления выполняются в одной транзакции PostgreSQL. Если SQL-операция завершается ошибкой, транзакция откатывается; локальный `SERIAL` не обновляется. Ограничения: подключение — 5 секунд; ожидание блокировки при чтении списка записей и применении — 5 секунд; отдельный SQL-запрос — 30 секунд. Это не общий предел времени всего процесса.

После успешного завершения транзакции PostgreSQL SINVER создаёт резервную копию SQLite и сохраняет локальный `SERIAL`. **Единой транзакции для PostgreSQL и SQLite нет:** если последнее действие завершится ошибкой, PowerDNS уже будет обновлён. Порядок восстановления описан ниже.

### SERIAL

Новый номер имеет формат `YYMMDDhhmm`: год из двух цифр, месяц, день, час и минута. Например, `2610071530` соответствует 7 октября 2026 года, 15:30 **по часовому поясу хоста SINVER**. Текущая реализация использует локальное время; UTC получается только при настройке хоста или процесса на UTC.

> Номер не гарантированно увеличивается: две отправки за одну минуту получают одинаковый `SERIAL`, а изменение времени хоста может дать меньший номер. Перед подтверждением сверяйте **New SERIAL** с **Remote SERIAL**. Для зон с вторичными DNS-серверами это критично: они могут не получить изменение при прежнем или меньшем номере. Подробности — в [текущих проблемах](11_Current_Issues_RU.md#serial-не-гарантирует-увеличение).

### Проверка результата

Для локальной установки из быстрого старта запросите запись непосредственно у PowerDNS, минуя обычный рекурсивный DNS-сервер:

```bash
dig @127.0.0.1 app-01.infra.example.net A +norecurse +noall +answer
```

Ожидаемый ответ:

```text
app-01.infra.example.net. 3600 IN A 192.0.2.10
```

Число `3600` может уменьшаться при ответе из кеша. Для удалённого PowerDNS замените `127.0.0.1` на его доступный адрес. Запрос `SOA` проверяет опубликованный номер версии:

```bash
dig @127.0.0.1 infra.example.net SOA +norecurse +noall +answer
```

Пример ожидаемого ответа, если в зоне заданы интервалы из быстрого старта:

```text
infra.example.net. 3600 IN SOA ns1.infra.example.net. hostmaster.infra.example.net. 2610071530 3600 600 1209600 300
```

Фактический номер должен совпадать с `New SERIAL` применённого плана и сохранённым `SERIAL` в SINVER. SINVER не очищает кеш PowerDNS и не отправляет уведомления вторичным серверам. Если непосредственно в БД данные новые, а DNS возвращает прежние, проверьте кеш и конфигурацию репликации PowerDNS.

### Резервная копия и восстановление

Автоматические копии SINVER содержат **SQLite, включая параметры подключения**, но не БД PowerDNS. На хосте PostgreSQL перед первой отправкой можно сохранить полный архив PowerDNS в текущем каталоге:

```bash
umask 0077
sudo -u postgres pg_dump --format=custom powerdns > powerdns-before-sinver.dump
```

`umask` ограничивает доступ к новому файлу владельцем; `pg_dump` читает БД `powerdns` и записывает архив. Выполняйте команду в предназначенном для резервных копий каталоге. Архив содержит все зоны этой БД; восстановление всего архива затронет их все.

Если применён неправильный план, автоматической кнопки отмены нет. Восстановите записи средствами PostgreSQL/PowerDNS из проверенной копии либо исправьте инвентарь и подготовьте новый план. При восстановлении старых DNS-данных назначьте `SOA` номер, который вторичные серверы примут как более новый.

Если PostgreSQL обновился, а локальный `SERIAL` не сохранился, сначала устраните ошибку записи или резервного копирования SQLite. Затем прочитайте фактический `SOA` в PowerDNS и укажите его `SERIAL` в карточке зоны SINVER. Не повторяйте принудительную отправку до проверки обеих БД.

### Частые сообщения

| Сообщение | Действие |
| --- | --- |
| `psycopg2 is not installed` | Установите драйвер PostgreSQL в окружение Python, которым запускается SINVER |
| `PostgreSQL connection data is incomplete` | Заполните адрес PostgreSQL и пользователя в карточке зоны |
| `Domain … not found in PowerDNS` | Создайте зону в PowerDNS и проверьте совпадение её имени с полем `Zone` |
| `Expected exactly 1 SOA record …` | Исправьте отсутствующую или дублирующуюся `SOA` в PowerDNS |
| `Local SERIAL is out of sync with Remote SERIAL.` | Сверьте текущую зону PowerDNS с инвентарём; затем согласуйте `SERIAL` или осознанно продолжите подготовку плана |
| `PowerDNS apply failed: …` | Проверьте доступность PostgreSQL, права пользователя, блокировки и текст ошибки; после исправления подготовьте новый план |

## Bind9

Блок **Bind9** содержит отдельный выбор **Zone** и кнопку **Generate config**. Кнопка скачивает файл `<zone>.db`, например `infra.example.net.db`. Это **файл записей зоны**, а не полная конфигурация службы BIND9.

В файл попадают `$TTL 3600`, одна `SOA` с новым `SERIAL` и те же `A`/`AAAA`, которые SINVER формирует для PowerDNS. Другие типы записей, в том числе `NS`, в экспорт не входят. Номер в SQLite не изменяется. Подключение к PostgreSQL для экспорта не требуется.

Перед установкой файла на DNS-сервер:

1. Добавьте необходимые `NS` и остальные записи зоны. При замене существующего файла сохраните из него нужные `MX`, `TXT` и другие записи.
2. Проверьте, что `MNAME` и `RNAME` в строке `SOA` — полные имена с завершающей точкой, например `ns1.infra.example.net.` и `hostmaster.infra.example.net.`. Экспорт копирует эти поля дословно; без точки BIND допишет имя зоны.
3. Проверьте увеличение `SERIAL` относительно опубликованной зоны.
4. Проверьте синтаксис, затем разместите файл и перезагрузите зону средствами BIND9.

Для проверки нужен `named-checkzone` из пакета `bind9-utils`. На Ubuntu/Debian установите утилиты BIND командой:

```bash
sudo apt install bind9-utils
```

Следующая команда проверяет подготовленный файл, не публикуя его:

```bash
named-checkzone infra.example.net ./infra.example.net.db
```

Ожидаемый результат **после добавления необходимых `NS` и проверки имён**:

```text
zone infra.example.net/IN: loaded serial 2610071530
OK
```

Если вывод содержит `has no NS records`, файл ещё не подготовлен к публикации. Проверка синтаксиса не подтверждает доступность DNS-сервера или делегирование зоны. SINVER не копирует файл в BIND9, не обновляет его конфигурацию и не перезагружает службу; эти действия выполняет администратор.
