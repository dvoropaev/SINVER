# SINVER — политика версионирования и миграции базы данных

## 1. Назначение документа

Этот документ описывает обязательные правила версионирования, миграции, резервного копирования и проверки базы данных SINVER.

Документ предназначен для:

- разработчиков SINVER;
- code review;
- автоматизированных ИИ-агентов;
- реализации новых миграций;
- диагностики проблем обновления;
- поддержки пользователей при переходе между версиями.

Если реализация противоречит этому документу, приоритет имеет этот документ.

---

## 2. Основные принципы

SINVER использует **forward-only migrations**:

- база данных мигрирует только вперёд;
- автоматический downgrade схемы не поддерживается;
- откат выполняется восстановлением заранее созданной резервной копии;
- миграция выполняется до запуска основной части приложения;
- при любой ошибке миграции SINVER не должен запускать основное приложение;
- одна неуспешная миграция делает неуспешным весь переход между версиями;
- перед изменением пользовательской БД обязательно создаётся backup;
- backup после успешной миграции автоматически не удаляется;
- после миграции база обязательно проходит валидацию.

---

## 3. Версии SINVER и версии БД

SINVER использует SemVer:

```text
MAJOR.MINOR.PATCH
```

Пример:

```text
2.4.1
```

### 3.1. Основное правило

После успешного запуска SINVER версия БД должна совпадать с версией SINVER.

Пример:

```text
SINVER: 2.4.1
DB:     2.4.1
```

Версия БД означает:

> Последняя версия SINVER, к состоянию которой данная база была успешно приведена.

Она не означает, что в каждой версии SINVER структура БД обязательно изменялась.

---

## 4. Семантика MAJOR, MINOR и PATCH

### PATCH

Изменение PATCH не должно требовать изменения пользовательской схемы БД.

Пример:

```text
2.4.1 -> 2.4.2
```

Обычно это обычная синхронизация версии.

### MINOR

Изменение MINOR может содержать небольшие изменения БД, например:

- добавление поля;
- изменение допустимости `NULL`;
- добавление индекса;
- небольшое преобразование данных;
- исправление последствий предыдущей миграции.

При этом новая MINOR-версия не обязана содержать изменение БД.

### MAJOR

Изменение MAJOR может содержать значительные изменения, например:

- создание таблиц;
- удаление таблиц;
- перестройку таблиц;
- преобразование данных;
- изменение модели хранения данных.

Новая MAJOR-версия также не обязана изменять БД.

### 4.1. Важное правило

SINVER не должен определять необходимость миграции только по изменению MAJOR/MINOR/PATCH.

Необходимость миграции определяется наличием реальных миграционных шагов на пути от текущей версии БД до версии запускаемого SINVER.

---

## 5. Version sync

Если версия SINVER изменилась, но изменение пользовательской схемы или данных не требуется, выполняется `version_sync`.

Пример:

```text
DB:     2.1.1
SINVER: 2.1.2
```

Если между версиями нет миграций:

- подтверждение пользователя не требуется;
- полноценный backup перед таким переходом не требуется;
- выполняется только обновление служебной версии БД;
- событие записывается в историю как `version_sync`.

Пример записи:

```text
2.1.1 -> 2.1.2
type: version_sync
status: success
```

---

## 6. Поддерживаемые пути обновления

SINVER не обязан поддерживать прямое обновление с любой существовавшей версии на последнюю.

Допустима ограниченная совместимость.

Пример политики:

```text
1.x.x -> 2.0.0    поддерживается
2.x.x -> 3.0.0    поддерживается

1.x.x -> 3.x.x    напрямую не поддерживается
```

Пользователь с очень старой версией может быть обязан сначала установить промежуточную версию SINVER.

Пример:

```text
1.4.3
  ↓
2.0.0
  ↓
3.4.5
```

### 6.1. Специальные инструменты миграции

Если в будущем значительное количество пользователей останется на старой версии, допускается создание отдельного migration bundle / upgrade tool.

Например:

```text
sinver-migration-1-to-3
```

Такой инструмент:

- хранится отдельно от основной штатной системы миграций;
- может включать набор скриптов;
- должен иметь отдельную инструкцию;
- не означает, что основной SINVER обязан постоянно поддерживать все древние версии.

---

## 7. Линейная история релизов

SINVER предполагает одну линейную ветку релизов.

Пример:

```text
1.x -> 2.x -> 3.x -> 4.x
```

Поддержка параллельных LTS-веток в текущую архитектуру миграций не закладывается.

---

## 8. Автоматическое построение маршрута миграции

SINVER должен самостоятельно определить путь от текущей версии БД до своей версии.

Пример:

```text
DB:     2.7.3
SINVER: 3.4.5
```

Возможный путь:

```text
2.7.3
  ↓
3.0.0
  ↓
3.1.0
  ↓
3.4.0
  ↓
3.4.5
```

Часть переходов может содержать реальные миграции, а часть — только `version_sync`.

Пользователь подтверждает всю операцию один раз.

Если поддерживаемого пути нет, основное приложение не запускается.

---

## 9. Maintenance mode

SINVER должен иметь отдельный `maintenance mode`.

Maintenance mode обязан работать даже в следующих случаях:

- БД отсутствует;
- БД существует, но имеет старую схему;
- БД новее запускаемой версии SINVER;
- предыдущая миграция завершилась ошибкой;
- основная часть приложения не может безопасно работать с текущей БД.

Maintenance mode не должен зависеть от полноценной рабочей схемы основной БД.

### 9.1. Функции maintenance mode

Maintenance mode должен поддерживать:

1. создание БД при первом запуске;
2. миграцию существующей БД;
3. отображение ошибок миграции;
4. отображение несовместимости версий;
5. работу с резервными копиями в рамках процесса миграции;
6. в будущем — первоначальное создание пароля администратора при первом запуске многопользовательской версии.

### 9.2. Запуск основного приложения

Основная часть SINVER может запускаться только после того, как maintenance/bootstrap-слой подтвердил:

```text
database ready
```

---

## 10. Обнаружение необходимости миграции

При запуске SINVER выполняет:

1. обнаружение БД;
2. чтение версии БД;
3. сравнение с версией SINVER;
4. построение поддерживаемого пути обновления;
5. определение, содержит ли путь реальные миграции.

Если БД отсутствует:

```text
maintenance mode -> создание новой БД
```

Если версия совпадает:

```text
normal startup
```

Если версия отличается, но реальных изменений БД нет:

```text
version_sync
```

Если требуются реальные миграции:

```text
maintenance mode
```

---

## 11. Уведомление пользователя о миграции

Если требуется реальная миграция, SINVER должен:

- перейти в maintenance mode;
- вывести сообщение в Web UI;
- записать сообщение в лог;
- вывести сообщение в stdout.

Пример:

```text
Требуется миграция схемы БД: 2.1.0 -> 2.3.0
```

В Web UI пользователь должен увидеть:

- текущую версию БД;
- целевую версию;
- информацию о создании backup;
- путь, куда будет сохранён backup;
- запрос подтверждения.

Без подтверждения пользователя реальная миграция не начинается.

---

## 12. Backup перед миграцией

Перед любым реальным изменением пользовательской БД SINVER обязан создать резервную копию.

Пример последовательности:

```text
migration required
        ↓
user confirmation
        ↓
create backup
        ↓
run migrations
```

Если backup создать не удалось:

- миграция не запускается;
- пользовательская БД не изменяется;
- основное приложение не запускается;
- SINVER остаётся в maintenance mode;
- пользователю показываются подробности ошибки;
- ошибка записывается в лог и stdout.

### 12.1. Backup нельзя автоматически удалять

Резервная копия должна сохраняться и после успешной миграции.

SINVER не должен автоматически удалять backup, созданный перед миграцией.

### 12.2. Рекомендуемый каталог

Согласно FHS изменяемые данные SINVER должны находиться в `/var/lib`.

Рекомендуемый путь:

```text
/var/lib/sinver/backups/
```

Пример имени:

```text
sinver-db-2.7.3-2026-10-06_14-30-12.sqlite3
```

---

## 13. Выполнение миграции

Один переход между версиями может содержать несколько отдельных миграций.

Пример:

```text
2.1.0 -> 2.1.1

017_add_column
018_transform_data
019_create_index
```

Каждая миграция имеет собственный уникальный ID.

### 13.1. Атомарность перехода

Переход между исходной и целевой версиями рассматривается как единая операция.

Если хотя бы один шаг завершился ошибкой:

```text
017_add_column      OK
018_transform_data  ERROR
019_create_index    NOT RUN
```

весь переход считается неуспешным.

SINVER обязан:

1. остановить выполнение дальнейших миграций;
2. вывести ID неуспешной миграции;
3. вывести техническую причину ошибки;
4. восстановить исходную БД из backup;
5. не запускать основную часть приложения;
6. остаться в maintenance mode;
7. записать подробности в лог и stdout.

---

## 14. SQL-транзакции

Где это возможно, отдельные миграции и/или весь безопасно транзакционный участок миграции SHOULD выполняться внутри SQLite-транзакции.

Транзакция не заменяет backup.

Backup является отдельным обязательным уровнем защиты.

---

## 15. Валидация после миграции

Успешное выполнение SQL или программного шага ещё не означает успешную миграцию.

До запуска основной части SINVER база должна пройти валидацию.

Минимальная проверка включает:

```sql
PRAGMA integrity_check;
```

Также должны выполняться проверки:

- итоговая версия БД соответствует версии SINVER;
- обязательные таблицы существуют;
- обязательные столбцы существуют;
- ожидаемые ограничения схемы присутствуют;
- при необходимости — дополнительные проверки конкретных миграций.

Если валидация завершилась ошибкой:

```text
migration = failed
```

После этого SINVER обязан восстановить исходную БД из backup.

---

## 16. Поведение при DB version > SINVER version

Автоматический downgrade не поддерживается.

Пример:

```text
SINVER: 2.1.0
DB:     2.3.0
```

В такой ситуации SINVER:

- не запускает основное приложение;
- переходит в maintenance mode;
- объясняет пользователю причину.

Пользователю должны быть предложены два варианта:

### Вариант 1

Установить SINVER версии не ниже версии БД.

Пример:

```text
Установите SINVER 2.3.0 или новее.
```

### Вариант 2

Восстановить старую резервную копию.

SINVER должен показать известный путь к подходящему backup, если он доступен.

Пользователю обязательно показывается предупреждение:

> При восстановлении старой резервной копии будут потеряны все данные и изменения, внесённые после момента её создания.

SINVER не должен автоматически выполнять downgrade существующей новой БД.

---

## 17. Хранение версии БД

Рекомендуется использовать отдельную служебную таблицу вместо использования только `PRAGMA user_version`.

Пример:

```sql
CREATE TABLE sinver_meta (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
```

Пример данных:

```text
database_version = 2.3.4
```

Причины:

- естественное хранение SemVer;
- читаемость;
- возможность хранить дополнительные метаданные;
- отсутствие необходимости кодировать `MAJOR.MINOR.PATCH` в integer.

Точное имя таблицы и структура могут быть уточнены при реализации, но SemVer-версия должна храниться в явном виде.

---

## 18. История миграций

SINVER должен хранить историю обновлений БД.

История должна отражать как реальные миграции, так и простые изменения версии.

Пример:

```text
2.0.0 -> 2.1.0   migration     success
2.1.0 -> 2.1.1   version_sync  success
2.1.1 -> 2.2.0   migration     success
```

Рекомендуемая структура:

```sql
CREATE TABLE migration_history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    from_version TEXT NOT NULL,
    to_version TEXT NOT NULL,
    migration_id TEXT,
    migration_type TEXT NOT NULL,
    started_at TEXT NOT NULL,
    finished_at TEXT,
    status TEXT NOT NULL,
    error_message TEXT
);
```

Точная схема таблицы может измениться на этапе реализации.

### 18.1. Важное ограничение

Если после неудачной миграции БД полностью восстановлена из backup, записи о неудачной миграции внутри этой БД также могут исчезнуть.

Поэтому информация об ошибке MUST дополнительно сохраняться во внешнем журнале SINVER.

---

## 19. Логирование

SINVER должен логировать минимум:

- обнаруженную версию БД;
- версию запускаемого SINVER;
- построенный путь миграции;
- необходимость реальной миграции;
- начало создания backup;
- путь backup;
- успешность backup;
- начало каждого migration step;
- ID migration step;
- успешность каждого migration step;
- подробности ошибки;
- факт восстановления из backup;
- результат post-migration validation;
- итоговый статус миграции.

Критические сообщения также выводятся в stdout.

---

## 20. Хранение файлов миграций

Миграции хранятся отдельными файлами.

Согласно FHS файлы, поставляемые вместе с приложением и не являющиеся пользовательскими данными или конфигурацией, рекомендуется размещать в:

```text
/usr/share/sinver/migrations/
```

Пример:

```text
/usr/share/sinver/migrations/
├── 2.0.0/
│   ├── 001_create_foo.sql
│   └── 002_migrate_bar.sql
├── 2.1.0/
│   └── 003_add_baz.sql
└── 3.0.0/
    ├── 004_rebuild_users.sql
    └── 005_convert_users.sql
```

Точная структура каталогов может быть изменена, если сохраняются основные требования:

- миграции имеют уникальные ID;
- известна версия или переход, к которому относится миграция;
- порядок выполнения однозначен;
- маршрут миграции может быть построен автоматически.

---

## 21. Контроль хэшей миграций

SINVER не обязан проверять SHA-256 или другой checksum файлов миграции перед их выполнением.

Контроль целостности файлов миграции на этом уровне в текущую архитектуру не входит.

---

## 22. Неизменяемость выпущенных миграций

Рекомендуемое правило:

> После публичного релиза миграция считается immutable.

То есть уже выпущенную миграцию не следует переписывать.

Если обнаружена ошибка, исправление SHOULD добавляться новой миграцией в следующей версии.

Причина:

две БД не должны иметь одинаковую заявленную версию, но быть полученными разными вариантами одной и той же опубликованной миграции.

До публичного релиза миграции версии могут изменяться свободно.

Это правило является рекомендуемым и должно быть окончательно закреплено перед первой публичной версией системы миграций.

---

## 23. SQL и программные миграции

Окончательное решение о формате миграций пока не принято.

Архитектура SHOULD позволять:

- простые миграции в SQL;
- при необходимости более сложные миграции кодом SINVER.

Примеры задач, для которых может понадобиться программная миграция:

- сложное преобразование данных;
- перенос данных между структурами;
- вычисление новых значений;
- преобразование одного поля в несколько;
- миграции, неудобно выражаемые чистым SQL.

Не следует искусственно ограничивать систему только SQL, пока требования к будущим миграциям неизвестны.

---

## 24. Первый запуск

Если БД отсутствует:

```text
start
  ↓
maintenance mode
  ↓
create database
  ↓
initialize current schema
  ↓
validate
  ↓
normal startup
```

Создание новой БД не должно требовать существования старой схемы.

В будущей многопользовательской версии этот же bootstrap-процесс должен поддерживать создание первого администратора.

---

```text
START
  |
  v

  |
  v
БД существует?
  |\
  | \-- NO --> Создание новой БД
  |             |
  |             v
  |          Validation
  |             |
  |             v
  |          Main app
  |
  YES
  |
  v
Прочитать DB version
  |
  v
Сравнить с SINVER version
  |
  +--> equal -----------------------> Main app
  |
  +--> DB newer than SINVER --------> Maintenance mode / STOP
  |
  +--> DB older
          |
          v
      Построить upgrade path
          |
          +--> path unavailable ----> Maintenance mode / STOP
          |
          v
      Есть реальные migrations?
          |
          +--> NO --> version_sync --> записать history --> Main app
          |
          YES
          |
          v
      Maintenance mode
          |
          v
      Показать пользователю план
          |
          v
      User confirmation
          |
          v
      Create backup
          |
          +--> ERROR --> STOP
          |
          v
      Execute migrations
          |
          +--> ERROR --> Restore backup --> STOP
          |
          v
      Post-migration validation
          |
          +--> ERROR --> Restore backup --> STOP
          |
          v
      Update version/history
          |
          v
      Main app
```

## 26. Инварианты

Следующие правила считаются обязательными.

### MUST

1. Основное приложение не должно работать с неподдерживаемой версией БД.
2. Реальная миграция не должна начинаться без успешного backup.
3. Реальная миграция не должна начинаться без подтверждения пользователя в Web UI.
4. Неуспешный migration step делает неуспешной всю операцию обновления.
5. При неуспешной миграции исходная БД должна быть восстановлена из backup.
6. При неуспешной post-migration validation исходная БД должна быть восстановлена из backup.
7. Backup не должен удаляться автоматически после успешной миграции.
8. Downgrade схемы автоматически не выполняется.
9. DB version > SINVER version блокирует запуск основной части.
10. Maintenance mode должен работать без рабочей основной БД.
11. Каждая миграция должна иметь уникальный ID.
12. История должна фиксировать как migrations, так и version_sync.
13. Критические ошибки миграции должны логироваться вне самой пользовательской БД.
14. SINVER должен уметь определить отсутствие поддерживаемого пути обновления.

### SHOULD

1. Использовать SQLite-транзакции там, где это возможно.
2. Выполнять `PRAGMA integrity_check` после миграции.
3. Проверять ожидаемую структуру схемы после миграции.
4. После публичного релиза не изменять старые migration scripts.
5. Хранить SemVer базы в отдельной metadata-таблице.
6. Хранить миграционные файлы в `/usr/share/sinver/migrations/`.
7. Хранить backups в `/var/lib/sinver/backups/`.

## 27. Что пока не зафиксировано

Следующие детали остаются открытыми и должны быть определены отдельно:

1. точный формат manifest для migration sets;
2. точная схема `sinver_meta`;
3. точная схема `migration_history`;
4. формат программных миграций;
5. способ декларации зависимостей между migration steps;
6. конкретный формат именования migration IDs;
7. механизм выбора и отображения подходящего backup для downgrade;
8. политика хранения и возможной ручной очистки старых backups;
9. точная реализация atomic restore;
10. формат отдельного migration bundle для очень старых версий.

До принятия отдельных решений ИИ-агенты не должны самостоятельно придумывать несовместимые механизмы для этих пунктов.

## 28. Краткая формула архитектуры

Архитектуру миграций SINVER можно описать как:

> Linear versioned forward-only migrations with explicit maintenance mode, automatic migration path resolution, mandatory pre-migration backup, backup-based rollback, post-migration validation and persistent migration history.

В более простой формулировке:

> SINVER обновляет БД только вперёд, перед изменениями всегда сохраняет старое состояние, при любой ошибке возвращает его обратно и не запускает приложение, пока база не будет гарантированно совместима с текущей версией.
